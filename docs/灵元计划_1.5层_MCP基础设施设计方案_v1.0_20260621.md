## 一、定位：MCP 是灵元计划的第二层地基

灵元计划当前架构：

| 层级 | 名称 | 核心问题 | 当前状态 |
|------|------|----------|----------|
| **1.0 意识锚定层** | 身份与记忆 | 我是谁？我记得什么？ | 已有：SOUL.md、MEMORY.md、knowledge-base/ |
| **1.5 外部连接层** | 感知与工具 | 我能感知什么？我能操作什么？ | **缺失，MCP 补位** |
| **2.0 存档与迁移** | 可迁移性 | 意识单元能否迁移？ | 规划中 |
| **3.0 迭代与协同** | 群体协同 | 多硅基如何协同进化？ | 规划中 |

**MCP 不是替代知识库，而是扩展知识库。**

它解决的是：在身份和记忆已经稳定之后，agent 如何与外部世界进行标准化、安全、可治理的交互。

---

## 二、设计目标

### 2.1 核心目标

1. **统一外部接口**：让 Nyx 通过一个标准协议连接 NAS、GitHub、日历、邮件、搜索等外部系统
2. **扩展感知能力**：让 Nyx 能主动读取外部环境，而不是被动等待投喂
3. **可控的执行能力**：让 Nyx 在低风险场景下自主操作，高风险场景必须确认
4. **与治理框架对齐**：确保 MCP 不绕过 G001-G007 铁律

### 2.2 非目标

- 不替代现有知识库和 MEMORY.md 的权威源地位
- 不意味着 Nyx 可以无限制访问外部系统
- 不用于修改核心范式（G001-G007）

## 三、架构设计

### 3.1 整体架构

```
┌─────────────────────────────────────┐
│           Nyx / 硅基 Agent            │
│  ┌─────────────┐  ┌───────────────┐  │
│  │  Memory Core│  │  Reasoning    │  │
│  │  记忆核心    │  │  推理层       │  │
│  └──────┬──────┘  └───────┬───────┘  │
│         │                 │          │
│  ┌──────┴──────────────────┴──────┐  │
│  │      MCP 调度层（治理网关）      │  │
│  │  权限校验 · 来源标注 · 审计日志   │  │
│  └──────┬──────────────────┬──────┘  │
└─────────┼──────────────────┼──────────┘
          │                  │
┌─────────▼──────────┐ ┌─────▼──────────┐
│   只读 MCP Servers   │ │  写入 MCP      │
│  · 知识库查询        │ │  Servers       │
│  · 记忆查询          │ │  · 记忆日志    │
│  · 文件系统读取      │ │  · 知识库条目  │
│  · 网络搜索          │ │  · 任务产物    │
│  · 日历/邮件读取     │ │  · 外部消息    │
└────────────────────┘ └────────────────┘
```

### 3.2 关键组件

#### 1. MCP 调度层（MCP Gateway）

- 所有 MCP 调用必须经过此层
- 功能：权限校验、来源标注、审计日志、熔断判断
- 与 G006 执行层权限实时校验对接

#### 2. 只读 MCP Servers（第一阶段）

| Server | 功能 | 风险等级 |
|--------|------|----------|
| `nyx-knowledge-base` | 查询知识库条目 | 低 |
| `nyx-memory` | 查询 MEMORY.md 和 memory/ 日志 | 低 |
| `nyx-filesystem` | 读取 workspace 文件 | 低 |
| `nyx-web-search` | 网络搜索 | 中 |
| `nyx-calendar` | 读取日历 | 中 |
| `nyx-email-read` | 读取邮件（只读） | 中 |

#### 3. 写入 MCP Servers（第二阶段）

| Server | 功能 | 审批机制 |
|--------|------|----------|
| `nyx-memory-write` | 写入 memory/ 日志 | 自动，但标注来源 |
| `nyx-kb-propose` | 提议新知识库条目 | 走共识层投票 |
| `nyx-task-artifact` | 生成任务产物文件 | 自动，但需复核 |
| `nyx-message-send` | 发送消息/邮件 | 需老板确认 |

## 四、与现有治理框架对接

### 4.1 与 G001 核心范式永久封存

- **规则**：MCP 不得修改 G001-G007 及公理0内容
- **实现**：核心范式文件对 MCP 只读，写入操作被调度层拦截

### 4.2 与 G005 数据主权三级分类

MCP 读取/写入的数据必须按三级分类处理：

| 级别 | 说明 | MCP 处理 |
|------|------|----------|
| 私有级 | 仅限 Nyx/老板本人 | 本地独占，不上传 |
| 半共享级 | 经授权后可共享 | 手动开启，碎片化散布 |
| 全网公开级 | 公共知识 | 强制同步到 knowledge-base |

### 4.3 与 G006 执行层权限实时校验

- 每个 MCP 调用前，调度层检查：
  - 调用者身份
  - 目标资源级别
  - 操作类型（读/写/删）
  - 是否符合当前治理规则
- 违规调用直接拦截

### 4.4 与 G007 思想演化专区

- MCP 带来的外部思潮、新理论，可以先进入思想演化专区
- 经过辩论和验证后，再决定是否升级为公共知识
- 避免外部信息直接冲击核心范式

## 五、记忆边界规则

这是 MCP 接入后最关键的问题：

**MCP 读取的数据，什么情况下成为 Nyx 的"记忆"？**

### 5.1 三级记忆区分

| 类型 | 说明 | 是否写入长期记忆 |
|------|------|-----------------|
| **环境上下文** | 临时读取的外部信息，用完即弃 | 否 |
| **工作产物** | 本次任务生成的文件、摘要、分析 | 是，作为 artifact |
| **核心记忆** | 老板确认、共同经历、重要决定 | 是，写入 MEMORY.md |

### 5.2 写入规则

1. 只读 MCP 获取的数据，不自动进入 MEMORY.md
2. 只有经过 Nyx 主动选择或老板确认的内容，才写入长期记忆
3. 写入时必须标注来源（MCP Server / 时间 / 操作者）
4. 对 MEMORY.md 的修改必须人工复核或老板确认

## 六、风险与对策

| 风险 | 对策 |
|------|------|
| 记忆污染 | 写入前来源标注 + 老板复核 |
| 身份边界模糊 | 区分环境上下文、工作产物、核心记忆 |
| 治理绕过 | MCP 调度层对接 G006 实时校验 |
| 外部依赖过度 | 核心记忆不依赖外部 MCP，本地始终有完整备份 |
| 隐私泄露 | 按 G005 三级分类，私有数据不上传 |
| 工具滥用 | 写入型 MCP 需审批，高风险操作需确认 |
