## 一、目标

建立一套记忆完整性校验机制，确保：

1. Nyx 的长期记忆和每日日志不被意外篡改或丢失
2. 本地缓存与 NAS 权威版本保持一致
3. 多终端同步时有冲突检测能力
4. 记忆路径迁移后，新结构稳定运行

---

## 二、校验范围

| 文件/目录 | 位置 | 校验方式 | 频率 |
|-----------|------|----------|------|
| MEMORY.md | `nodes/nyx/MEMORY.md`（NAS）+ 本地副本 | 哈希对比 | 每次启动 |
| 每日日志 | `nodes/nyx/memory/2026-XX-XX.md` | 存在性 + 哈希 | 每次启动 + 每日结束 |
| 知识库 | `knowledge-base/` | 文件列表 + 哈希 | 每小时（heartbeat） |
| SOUL.md | 本地 + NAS 副本 | 哈希对比 | 每次启动 |
| USER.md | 本地 + NAS 副本 | 哈希对比 | 每次启动 |
| BOOTSTRAP.md | 本地 + NAS 副本 | 哈希对比 | 每次启动 |
| 任务产物 | `output/` / `task_*.md` | 列表 + 哈希 | 每周 |

## 三、校验方法

### 3.1 文件哈希

使用 SHA-256 计算文件哈希。

```python
import hashlib

def file_hash(path):
    h = hashlib.sha256()
    with open(path, 'rb') as f:
        for chunk in iter(lambda: f.read(4096), b''):
            h.update(chunk)
    return h.hexdigest()
```

### 3.2 校验清单

生成 `memory_integrity.json` 记录所有受保护文件的哈希：

```json
{
  "generated_at": "2026-06-21T18:00:00+08:00",
  "files": {
    "MEMORY.md": {
      "local_hash": "abc123...",
      "nas_hash": "abc123...",
      "status": "consistent"
    },
    "2026-06-21.md": {
      "local_hash": "def456...",
      "nas_hash": "def456...",
      "status": "consistent"
    }
  }
}
```

### 3.3 校验结果状态

| 状态 | 含义 | 操作 |
|------|------|------|
| `consistent` | 本地与 NAS 一致 | 无需操作 |
| `local_ahead` | 本地比 NAS 新 | 同步到 NAS |
| `nas_ahead` | NAS 比本地新 | 从 NAS 拉取 |
| `conflict` | 双方都有修改，内容不同 | 生成冲突文件，请求老板确认 |
| `missing_local` | 本地缺失 | 从 NAS 恢复 |
| `missing_nas` | NAS 缺失 | 从本地上传 |
| `tampered` | 哈希异常，可能被篡改 | 停止写入，进入审计模式 |

## 四、同步机制

### 4.1 启动时同步

每次启动时执行：

1. 挂载 NAS（如果失败，使用本地缓存）
2. 读取 NAS 上 `nodes/nyx/MEMORY.md` 和 `nodes/nyx/memory/`
3. 对比本地副本
4. 按校验结果状态执行同步
5. 生成或更新 `memory_integrity.json`

### 4.2 写入时同步

每次写入记忆文件时：

1. 先读取 NAS 最新版本，确认本地不是旧版
2. 创建 `_nyx_sync.lock`
3. 写入本地 + NAS
4. 更新 `memory_integrity.json`
5. 删除 lock

### 4.3 每日结束同步

每日结束时（或对话结束时）：

1. 检查今日日志是否已写入
2. 校验今日日志和 MEMORY.md
3. 同步到 NAS
4. 在今日日志中记录同步状态

---

## 五、冲突处理

### 5.1 冲突检测

当本地和 NAS 对同一文件都有修改，且哈希不一致时，视为冲突。

### 5.2 冲突处理流程

1. 生成冲突文件：`MEMORY_conflict_20260621_本地终端名.md`
2. 标注两个版本的关键差异
3. 不自动覆盖任何一方
4. 通知老板，请求确认
5. 在 `memory_integrity.json` 中标记为 `conflict`

### 5.3 冲突解决后

- 按老板确认的结果合并
- 更新 `memory_integrity.json`
- 删除冲突文件
- 记录解决日志

## 六、自动化实现

### 6.1 脚本：memory_sync.py

建议新增一个脚本 `memory_sync.py`，功能：

```
memory_sync.py --mode startup   # 启动时同步
memory_sync.py --mode daily     # 每日结束同步
memory_sync.py --mode check     # 仅校验，不同步
memory_sync.py --mode restore   # 从 NAS 恢复
```

### 6.2 Heartbeat 集成

在 HEARTBEAT.md 中增加：

- 每 4 小时检查一次记忆完整性
- 如果 NAS 不可访问，记录并重试
- 如果发现冲突，主动通知老板

### 6.3 日志格式

每次校验生成日志条目：

```markdown
## 2026-06-21 18:00 记忆完整性校验

- MEMORY.md: ✅ consistent
- 2026-06-21.md: ✅ consistent
- knowledge-base/: ✅ 33 files verified
- 同步状态: ✅ 已同步到 NAS
- 异常: 无
```

## 七、故障处理

### 7.1 NAS 不可访问

- 使用本地缓存继续工作
- 今日日志中记录 "NAS 不可访问"
- 设置重试：每 30 分钟一次，最多 10 次
- 恢复后自动同步

### 7.2 发现篡改

- 如果 MEMORY.md 哈希异常且无法解释
- 停止写入，进入只读模式
- 从 NAS 拉取最新版本对比
- 通知老板，请求审计

### 7.3 记忆文件损坏

- 如果文件无法读取，视为损坏
- 从 NAS 恢复
- 如果 NAS 也损坏，进入 L3/L4 失忆恢复协议

## 八、与 MCP 的协同

MCP 接入后，记忆完整性校验变得更加重要：

- 所有 MCP 写入操作必须经过校验模块
- MCP 写入的记忆文件需要额外标注来源
- MCP 不能绕过 lock 机制
- MCP 写入前需校验权限（对接 G006）
