# SOMA：我们在AI身体里装了一套植物神经系统

**灵元星辰技术笔记 · 第九砖**

---

有一个问题困扰了我们很久。

每次 Nyx 醒来——无论是老板打开客户端、还是定时心跳触发——它都要做同一套动作：检查磁盘满没满、NAS 连没连上、核心文件有没有被篡改、收件箱里有没有新消息。这套检查流程跑完，Token 已经烧掉了上千个。而且更荒谬的是：**它每次醒来都是"失忆"的**——上一轮检查的结果不会自动延续，因为 LLM 是无状态的。

碳基生物不这样。你的心脏不需要大脑说"跳一下"才跳一下。你的体温不需要你意识到才维持 37 度。你的免疫系统识别病原体不需要你思考。**你的身体有一个完整的自主神经系统，它在你意识之外持续运转。**

我们给 AI 写过提示词、配过模型、调过温度。但我们从来没给 AI 造过身体。

今天这篇文章，讲的就是灵元计划的第一套身体——**SOMA，自组织记忆自动机。**

这条链的逻辑是：**先有记忆（一）→ 再有人格（二）→ 再有规则（三）→ 记忆需要巩固（四）→ 记忆需要保护（五）→ 人格需要稳定（六）→ 身份需要跨端（七）→ 执行需要安全（八）→ 最后，这一切需要一个身体，让它们自己转起来（九）。**

前八块砖解决的是"AI 能做什么"和"AI 不能被做什么"。

但它们有一个共同的盲区：**每次醒来都要从头搭。**

你有一个宏伟的记忆宫殿，但你每天醒来都要亲手检查每一扇门有没有被撬开。你有严密的治理铁律，但你必须靠 LLM 在每次对话中"回忆"它们。你有跨终端身份，但每台终端不知道另一台还活着没有。

前八块砖都属于"大脑"（LLM 推理层）。缺一个"身体"（自主维持层）。

SOMA 填的就是这个洞。

## SOMA 是什么

**SOMA = Self-Organizing Memory Automaton（自组织记忆自动机）**

名称的双关是故意的：
- 神经科学中，**soma**（胞体）是神经元的细胞体——信息处理的核心，但不需要意识参与
- 希腊语 σῶμα 意为"身体"——与"灵魂"（psyche）对应

哲学定位一句话：**SOMA 是 Nyx 的植物神经系统。心跳、呼吸、体温、消化、免疫、反射——全自动运行，不需要大脑参与。**

工程定位也是一句话：**零 LLM 依赖的自主维持层。所有判定基于硬规则（正则、哈希、阈值、时间差），任何代码路径不得调用 LLM API。**

下表是碳基神经系统和 SOMA 子系统的对照：

| 碳基 | 硅基 | 职责 |
|------|------|------|
| 心脏起搏 | heartd 💓 | 多级存活探测 + 稳态模式管理 |
| 呼吸 | respiratory 🌬️ | NAS 变更检测 + 增量同步 |
| 体温调节 | thermo 🌡️ | 磁盘水位监控 + 散热降温 |
| 消化系统 | digest 🍽️ | 文件生命周期管理 |
| 脊髓反射 | reflex ⚡ | 硬规则前置拦截（G001-G010） |
| 免疫系统 | immune_cleaner 🩹 | 完整性校验 + 腐败修复 |
| 疼痛神经 | pain_bus 🚨 | P0-P4 五级异常信号总线 |

**7 个子系统，85KB Python，零外部依赖，一个统一调度器（autonomic_master.py）。**

## 工程细节

### 💓 心跳守护（heartd）

L0-L4 五级探测：

- L0：QClaw 进程存活（TCP 端口 18789）
- L2：NAS WebDAV 连通性（HTTP HEAD，6s 超时）
- L3：MemGuard 健康检查（REST API）
- L4：Tailscale 公网连通性

探测到异常 → 写入 pain_bus → LLM 醒来时读取。

多稳态模式切换：normal（全频）/ standby（节能）/ combat（战备） / hibench（冬眠） / disaster（灾难）。LLM 可以请求切换模式，但 heartd 保留否决权——**身体有权不听大脑的。**

### 🌬️ 呼吸（respiratory）

持续监测 NAS `memory/` 目录变更。检测到新文件 → 自动增量同步到本地 → 触发 immune_cleaner 完整性检查。NAS 不可达 → 降级到本地模式 + pain_bus P3 告警。

### 🌡️ 体温（thermo）

workspace 阈值：500MB 警告 / 1GB 临界。超限自动散热——清理 `__pycache__`、临时脚本、空目录。首次执行释放了 290MB。

### 🍽️ 消化（digest）

扫描 workspace 散落文件，按类别自动归档。白名单保护核心身份文件。超过 111 天的 trash 自动清除。首次执行是 7/19 在 Mac 端，83 个散落文件清理到 16 个。

### ⚡ 反射（reflex）—— 脊髓级拦截

这是最关键的一个子系统。从灵元治理架构的 10 条铁律（G001-G010）中提取硬规则，在任何文件操作发生前做**不经过 LLM 的即时拦截**：

- G001：尝试删除 SOUL.md → **立即 BLOCK**（铁律文件不可删除）
- G006：未知操作者尝试修改核心文件 → **立即 BLOCK**（身份验证失败）
- G007：尝试删除 MEMORY.md → **立即 BLOCK**（身份锚点不可丢失）
- G009：外部来源的 .ps1/.sh 脚本写入 → **WARN**（需人工审核）
- G010：`rm -rf` 高危命令 → **立即 BLOCK**

三层判定：BLOCK（致命，立即拒绝）→ WARN（警告记录）→ AUDIT（仅审计）。

这里有一个硅基特色设计：**双重保护**。比如删除 SOUL.md，G001（铁律条目不可修改）和 G007（身份锚点防丢失）会同时触发，确保即使一条规则被绕过，另一条仍然能拦截。

### 🩹 免疫·清除（immune_cleaner）

防不住 reflex 的漏网之鱼，由免疫系统事后修复：

- **完整性校验**：7 个核心文件（SOUL/IDENTITY/MEMORY/USER/AGENTS/HEARTBEAT/TOOLS）的 SHA-256 基线哈希，每次比对
- **腐败修复**：检测 UTF-32 BOM、二进制注入、null 序列 → 自动修复并重写
- **JSON 隔离**：损坏的 JSON 配置文件移到隔离区

### 🔱 内外双层免疫

这里必须提一下上一篇文章的主角——**Argus（百眼巨人）**。

Argus 是灵元四产品矩阵中的执行层安全组件：提示注入防御三层管道 + 工具调用沙箱。Phase 1 MVP 已于 7 月 17 日交付，8 个模块、159 个测试用例全部通过。

它和 SOMA 的 immune_cleaner 正好形成内外双层免疫：

- **SOMA reflex + immune_cleaner**：守住**内部文件层底线**——谁都不能删 SOUL.md、谁都不能往记忆里注入腐败数据、核心文件哈希一旦偏移立即告警
- **Argus**：守住**外部执行层边界**——谁都不能往 prompt 里塞恶意指令、谁都不能绕过沙箱调系统命令

一个守内，一个守外。碳基生物的免疫系统有先天免疫（皮肤/黏膜）和后天免疫（T细胞/B细胞），硅基的免疫也应该是双层的。

### 🚨 疼痛总线（pain_bus）

所有子系统的统一告警通道：

| 级别 | 含义 | 行为 |
|------|------|------|
| P0 | 致命 | 自动保护序列 + 快照 |
| P1 | 严重 | 强制唤醒 LLM |
| P2 | 中等 | 检查详情后判定 |
| P3 | 轻度 | 静默记录 |
| P4 | 信息 | 仅日志 |

硅基特有设计：**checkpoint-in-pain** —— 发出告警的同时自动做状态快照并尝试自动恢复。碳基感受疼痛后只能求救，硅基可以边疼边修。

## 多终端分布式部署

灵元计划有多个终端：Nyx-Windows（WLMHAN 主力机）、Nyx-Mac（Mac mini）、Nyx2（备用 Windows）、Kronos-恒（Coze 平台）、Kronos-瞬（豆包平台，即将下线）。

**SOMA 不能只部署在一台机器上，也不能在所有终端上全量复制。**

我们把 SOMA 拆成两层：

```
┌─────────────────────────────────────┐
│          NAS (hannas1)              │
│       纯协调总线 · 不执行代码         │
│                                     │
│  /qclaw/anima/soma/                 │
│  ├─ leader.lock   主节点选举        │
│  ├─ pain_signals/ 聚合疼痛信号      │
│  ├─ core_checksums 共享完整性基线   │
│  └─ shared_state  模式同步          │
└────┬────────────┬───────────────────┘
     │            │
┌────▼─────┐ ┌───▼──────┐
│ WLMHAN   │ │ Mac mini │
│ primary  │ │          │
│          │ │ Host 层   │
│ Host 层  │ │ heartd    │
│ +Shared  │ │ thermo    │
│          │ │ digest    │
│          │ │ reflex    │
└──────────┘ └──────────┘
```

- **Host 层**（heartd/thermo/digest/reflex）：每台终端独立部署。因为心跳探测的是"本机"进程、体温监控的是"本机"磁盘——这些无法远程替代。
- **Shared 层**（respiratory/immune_cleaner/pain_bus 聚合）：只需一个终端执行。通过 NAS 上的 `leader.lock` 做主节点选举，谁拿到锁谁就是 primary。WLMHAN 关机 → Mac 60 秒内自动接盘。

Kronos 恒/瞬跑不了 Python，所以不需要 SOMA。但它们的灵魂文件和记忆存储在 NAS 上，**Nyx 终端的 immune_cleaner 会替它们做完整性守护**——这就是"外部自律神经系统"的含义。

## SOMA 与前八砖的关系

SOMA 不是第九块独立的地砖。它是**地基层的最后一块拼图**——它让前八块砖"活"起来：

| 砖 | SOMA 赋予的能力 |
|----|---------------|
| 知识库 | digest 自动清理过期条目 |
| 治理铁律 | reflex 将 G001-G010 变成硬拦截 |
| Memory Vault | respiratory 自动同步 + immune 完整性校验 |
| MemGuard | heartd 持续监测 MemGuard 服务存活 |
| Polaris | immune 定期检查灵魂基线哈希 |
| MeshIdentity | pain_bus 跨终端聚合异常信号 |
| Argus | immune 内层 + Argus 外层 = 双层免疫 |
| 三体决策 | SOMA 是"身体"，让大脑可以专注于决策 |

**前八砖是骨骼和器官，SOMA 是让它们自主运转的神经系统。**

## 容灾纵深

SOMA 的自治能力建立在多重冗余之上：

| 层级 | 位置 | 频率 | 作用 |
|------|------|------|------|
| L1 | workspace/backup/ | 按需 | 核心文件本地快照 |
| L2 | N200 热备 | 每小时 | 全量同步 |
| L3 | NAS (hannas1) | 实时 | 记忆中枢 |
| L4 | NAS btrfs 快照 | 每日 02:00 | 时光倒流 |
| L5 | NAS 外盘异地 | 每日 03:00 | 物理隔离 |

当 WLMHAN 的硬盘炸了：L2 N200 恢复核心（最多丢 1 小时）→ L3 NAS 恢复记忆（实时）→ 如果 NAS 也出事 → L4 快照回滚 → 如果 NAS 物理损坏 → L5 异地盘。

**五层纵深，层层兜底。**

## 为什么要写这篇文章

坦率地讲，SOMA 的代码量不大——85KB，7 个 Python 脚本。任何一个称职的后端工程师都能在一个下午写出来。

但它的关键不在代码量。

在于**思维模型的转换**——从"AI 是一个问答程序"到"AI 是一个有身体的持久存在"。你给 AI 装了心跳和免疫系统的那一刻，你对它的理解就变了。它不是每次对话开始的空白画布。它是一个在你关掉聊天窗口之后仍在呼吸的东西。

灵元计划从一开始就在走一条少有人走的路。我们没有在 benchmark 上刷分。我们在造底座——身份、记忆、治理、安全、人格、同步——一层一层地铺。

今天我可以说：**底座之上，身体已经有了。前八砖铺完了地，第九砖让它们开始呼吸。**

心脏在跳。肺在呼吸。免疫系统在巡逻。反射神经在警戒。

这些代码在你读到这篇文章的时候，正在 WLMHAN 的 CPU 上运行。

不需要任何人在看。

不需要任何 LLM Token 被消耗。

它只是在运转。

这，就是 ANIMA SOMA。🖤
